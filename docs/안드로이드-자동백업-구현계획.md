# 땅콩페밀리 — 안드로이드 자동 백업 앱 구현 계획

> 작성 기준: 현재 코드베이스(master 브랜치) 분석 결과 반영
> 목표: 스토어 없이 설치하는 현 PWA 방식을 유지하면서, **안드로이드에서 백그라운드 자동 사진/영상 백업**을 지원한다.

---

## 0. 한눈에 보기 (결정 사항)

| 항목 | 결정 |
|---|---|
| 앱 형태 | 기존 React 웹앱을 **Capacitor로 감싼 안드로이드 네이티브 앱(APK)** |
| 배포 | 스토어 없이 **NAS에서 APK 직접 다운로드(사이드로딩)** |
| iOS | **기존 PWA 그대로 유지** (자동 백업 미지원, 수동 업로드) |
| 사용 대상 | **master(한승하/황하람) 전용.** APK는 master에게만 배포, 일반 사용자는 백업 기능/권한 미부여 |
| 백업 대상 | 새 사진/영상 → **master 본인 개인공간(visibility=private)** 으로 |
| 백업 폴더/조건 | 폴더·WiFi전용·충전·배터리 모두 **사용자가 선택(토글)** |
| 공유 | 개인공간에 쌓인 것 중 **직접 고른 것만** 공유 갤러리로 |
| 로그인 | 기기당 **영속 로그인** (refresh token + 보안 저장소) |
| 앱 업데이트 | 인앱 **"업데이트 있음 → 다운로드 → 설치"** (윈도우식) |
| UI/기능 | 웹과 **100% 동일** (Capacitor가 기존 웹앱을 그대로 로드) |

## 1. 목표 & 비목표

### 목표
- 안드로이드 사용자가 APK를 한 번 설치하면, 새로 찍은 사진/영상이 **백그라운드에서 자동으로 NAS에 백업**된다.
- 백업본은 본인 **개인공간**에 쌓이고, 가족과 공유할 것만 직접 공유한다.
- 한 번 로그인하면 그 기기에서는 **다시 로그인 화면을 보지 않는다**.
- 네이티브 변경이 있을 때만 **인앱 업데이트**로 새 APK를 받는다. UI/기능 추가는 지금처럼 무마찰 반영.

### 비목표 (이번 범위 아님)
- iOS 자동 백업 (PWA 유지로 합의됨).
- 실시간(촬영 즉시) 백업 보장 — 안드로이드 백그라운드 정책상 수 분~수십 분 지연 허용.
- 청크/이어받기(resumable) 업로드 — v1은 단일 POST + 재시도. (향후 과제로 분리)
- Google Play 배포.

## 2. 현재 코드베이스 분석 (이 계획의 전제)

### 2.1 인증 (server/auth.ts)
- `generateToken()` (`auth.ts:62`): `jwt.sign({ userId, role }, JWT_SECRET, { expiresIn: '4h' })` — **4시간 만료, refresh token 없음**.
- `authenticate()` (`auth.ts:32`): **쿠키에서만** 토큰을 읽음 (`fpauth`/`fauth`, `X-App-Mode` 헤더로 구분). Bearer 헤더 미지원.
- OAuth(Kakao) 콜백이 쿠키를 굽고 `/`로 리다이렉트.
- → **백그라운드 업로더(WebView 바깥의 네이티브 코드)가 쓸 자격증명이 없다.** refresh token + Bearer 지원이 필요.

### 2.2 업로드 (server/routes/media.ts)
- `POST /api/media/upload?visibility=private|shared` (`media.ts:148`) — multipart 단일 파일, 최대 10GB(`index.ts:28`).
- **비공개 업로드 게이트** (`media.ts:182`): `vis = (visibility === 'private' && role === 'master') ? 'private' : 'shared'`
  → **현재 개인공간은 master(한승하/황하람)만 사용 가능.** ⚠️ 결정 D1 참고.
- 중복 제거(dedup): 해시 기반.
  - 사전 체크: `POST /api/media/check-duplicate` (`media.ts:135`).
  - 업로드 시 서버도 재계산해 중복이면 스킵(`media.ts:172`).
- **빠른 해시 규약** (네이티브가 동일하게 구현해야 함):
  - 파일 ≤ 4MB: 전체 바이트의 SHA-256.
  - 파일 > 4MB: `SHA-256( 앞 4MB ‖ 뒤 4MB ‖ 파일크기 8바이트 )`.
    - 파일크기는 **IEEE754 double, big-endian 8바이트** (`media.ts:529` `writeDoubleBE`, 클라이언트 `api.ts:493` `setFloat64`).
  - 참조 구현: 서버 `computeQuickHash()` (`media.ts:512`), 웹 `api.hashFile()` (`api.ts:483`).

### 2.3 미디어 스키마 (server/db.ts)
- `media` 테이블: 기본 컬럼 + 마이그레이션으로 추가된 `source`('local'|'peanut'|'family'), `visibility`(default 'shared'), `ownerId`.
- 비공개 목록 조회 `GET /api/media?scope=private` 도 **role master만** 허용(`media.ts:38`).
- `lat`/`lng`/`place`/`takenAt` 등 EXIF 기반 메타가 갤러리·여행앨범에서 사용됨 → **백업 시 EXIF(GPS/촬영시각) 보존 필요** (`ACCESS_MEDIA_LOCATION` 권한).

### 2.4 서버/빌드/PWA
- 단일 Fastify (`index.ts`): CORS `origin:true, credentials:true`, SPA를 `dist/public`에서 서빙, SPA fallback.
- Vite build → `dist/public` (`vite.config.ts:22`).
- PWA: `public/manifest.json`, `public/sw.js`(network-first + Web Push 이미 구현됨, `push_subscriptions` 테이블 존재).
- 운영: NAS Docker, `127.0.0.1:12290:2290`, DSM 리버스 프록시가 `https://syngha.synology.me:2290` 처리(Let's Encrypt 정상 인증서).

## 3. 확정된 결정

> 모두 합의 완료. 아래 방향으로 구현한다.

### D1. 개인공간을 누가 쓰나 → **(A) master 전용** ✅ 확정
- 자동 백업은 **master(한승하/황하람)만** 사용. APK도 master에게만 배포.
- 일반 사용자는 백업 기능 노출 안 함 + 백업 권한(미디어/포그라운드 등) **미요청**.
- **결과: 백엔드 가시성 로직 변경 0.** `visibility=private`가 이미 master 전용이므로(`media.ts:182`), master가 `visibility=private`로 업로드하면 그대로 동작. **개인공간 일반화(구 P2 단계) 불필요 → 삭제.**
- 게이트 구현:
  - 웹 백업 UI: `Capacitor.isNativePlatform() && user.role === 'master'` 일 때만 표시.
  - 네이티브: master 토큰이 아니면 백업 워커/권한 요청 자체를 비활성.

### D2. 인증 모델 → **refresh token 도입** ✅ 확정
- 영속 로그인 + 백그라운드 업로드를 위해 refresh token 체계 추가. 세부 §5.

### D3. 무엇을 백업하나 → **폴더 선택 UI 제공** ✅ 확정
- 기기의 미디어 폴더 목록을 보여주고 **사용자가 백업할 폴더를 선택**(다중).
- 기본 선택: 카메라(DCIM/Camera). 스크린샷/다운로드 등은 기본 해제(원하면 추가).
- 사진만 / 사진+영상 토글.

### D4. 업로드 안정성 수준 (v1 범위)
- v1: **단일 multipart POST + WorkManager 재시도**(실패 시 처음부터 재업로드). 단순, 기존 API 그대로.
- 향후: 청크 이어받기(대용량 영상 효율↑). 별도 과제.

### D5. 백업 조건 → **사용자 선택(토글)** ✅ 확정
- WiFi 전용 / 충전 중에만 / 배터리 부족 시 중단 — 모두 설정에서 토글.
- 권장 기본값: WiFi 전용 ON, 충전 중에만 OFF, 배터리 부족 중단 ON (사용자가 변경 가능).

- 둘 사이는 Capacitor 커스텀 플러그인으로 통신(설정 전달, 상태 조회).

## 5. 인증 재설계 (영속 로그인 + 백그라운드 토큰)

### 5.1 토큰 구조
- **Access token**: 기존 JWT 유지(수명 4h → 그대로 또는 1h로 단축 가능). API 호출용.
- **Refresh token**: 신규. 장수명(예: 무기한, 폐기 전까지). 기기별 1개. 보안 저장소에 저장.

### 5.2 새 테이블 (마이그레이션, 비파괴)
```sql
CREATE TABLE IF NOT EXISTS device_sessions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  userId      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  tokenHash   TEXT NOT NULL UNIQUE,   -- refresh token의 SHA-256 (평문 저장 금지)
  deviceName  TEXT,                   -- "갤럭시 S24" 등 표시용
  createdAt   TEXT DEFAULT (datetime('now','+9 hours')),
  lastUsedAt  TEXT,
  revokedAt   TEXT                    -- 원격 로그아웃 시 set
);
```

### 5.3 새 엔드포인트 (server/auth.ts)
| 메서드/경로 | 인증 | 동작 |
|---|---|---|
| `POST /api/auth/device` | 쿠키(기존 세션) | refresh token 발급·저장(해시), 평문 1회 반환. WebView 로그인 직후 호출 |
| `POST /api/auth/token` | refresh token(body) | refresh 검증 → 새 access token 반환. 백그라운드/앱시작 시 |
| `GET /api/auth/sessions` | 쿠키/Bearer | 내 기기 세션 목록 |
| `POST /api/auth/sessions/:id/revoke` | 쿠키/Bearer | 해당 기기 원격 로그아웃 |

### 5.4 `authenticate()` 확장 (auth.ts:32)
- 기존 쿠키 경로 유지 + **`Authorization: Bearer <accessToken>` 헤더도 허용**.
- 우선순위: Bearer 있으면 Bearer, 없으면 기존 쿠키.
- 비파괴(웹은 계속 쿠키 사용).

### 5.5 영속 로그인 동작
1. 사용자가 WebView에서 카카오 로그인(기존 플로우) → 쿠키 세션 생성.
2. 앱이 `POST /api/auth/device` 호출 → refresh token 수령 → **네이티브 보안 저장소(EncryptedSharedPreferences/Keystore)** 에 저장.
3. 앱 시작/백그라운드 작업마다 네이티브가 `POST /api/auth/token`으로 access token 갱신.
4. 갱신한 access token을 **WebView 쿠키로 주입**(또는 Bearer 사용) → UI도 만료 없이 유지.
5. 사용자는 명시적 로그아웃(또는 원격 폐기) 전까지 재로그인 불필요.

> 백그라운드 백업은 사용자가 없을 때 돌아야 하므로 이 refresh 흐름이 **백업의 전제조건**이기도 하다.

## 6. 백업 엔진 (안드로이드 네이티브)

### 6.1 매니페스트 권한
> 권한 요청은 **master 로그인 사용자에게만** 수행한다(D1). 일반 사용자에게는 백업 UI/권한 요청을 노출하지 않는다.

| 권한 | 용도 |
|---|---|
| `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO` | 사진/영상 접근 (Android 13+) |
| `READ_EXTERNAL_STORAGE` (maxSdk 32) | 구버전 호환 |
| `ACCESS_MEDIA_LOCATION` | 원본 EXIF의 GPS 보존(여행앨범/지도용) |
| `POST_NOTIFICATIONS` | 백업 진행 알림 (Android 13+) |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC` | 백그라운드 업로드(Android 14+ 타입) |
| `RECEIVE_BOOT_COMPLETED` | 재부팅 후 백업 재스케줄 |
| `REQUEST_INSTALL_PACKAGES` | 자동 업데이트(APK 설치) |

### 6.2 새 사진 감지
- **커서 방식**: 마지막으로 처리한 MediaStore `DATE_ADDED`(또는 `_id`)를 저장.
- 트리거 시 `MediaStore.Images/Video`에서 커서 이후 항목만 쿼리(선택된 폴더 필터 적용).
- 트리거 2종:
  - **WorkManager 주기 작업**(최소 15분 간격) — 주력. 재부팅에도 재등록.
  - (옵션) 앱 포그라운드 동안 `ContentObserver`로 준실시간.

### 6.3 업로드 워커 (WorkManager)
순서:
1. access token 확보(없으면 refresh, 그래도 실패면 알림 "재로그인 필요" 후 종료).
2. 백업 대기 목록 산출(커서 이후 + 폴더 필터 + 사진/영상 설정).
3. 각 파일에 대해:
   a. **해시 계산**(§2.2 규약과 **바이트 단위로 동일**해야 dedup 일치).
   b. `POST /api/media/check-duplicate` → 중복이면 스킵하고 커서만 전진.
   c. `POST /api/media/upload?visibility=private` 로 업로드(Bearer).
   d. 성공 시 커서 전진 + 로컬 백업 기록(uploaded set).
4. 진행 중 **Foreground Service** + 알림("백업 중 12/40").
5. 실패는 WorkManager 백오프 재시도. 부분 성공 후 재개 가능(커서/uploaded set 기준).
- **제약(Constraints)**: WiFi 전용/충전/배터리 — D5 설정값을 WorkManager Constraints로.

### 6.4 개인공간 적재
- 업로드는 항상 `visibility=private` 로 → master 본인 개인공간에 적재.
- **백엔드 변경 없음**: 백업 사용자는 master뿐이고 `visibility=private`가 이미 master 허용(`media.ts:182`)이라 기존 게이트 그대로 통과.
- 사용자가 공유 갤러리로 올리고 싶으면 기존 **promote-to-shared** 흐름(이미 `api.promoteToShared` 존재) 사용.

### 6.5 신뢰성 — 삼성/Doze ⚠️
- One UI(갤럭시)는 백그라운드를 공격적으로 종료 → WorkManager 지연/누락 가능.
- 대응:
  - 앱 내 **"배터리 최적화 제외" + "절전 예외 등록" 안내 화면**(딥링크: `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`).
  - 최초 설정 마법사에서 1회 유도.
  - 백업은 실시간이 아니어도 되므로(지연 허용) 안내만 잘 하면 실용적.
- `RECEIVE_BOOT_COMPLETED` 수신 → WorkManager 재등록.

## 7. 백업 설정 UI + Capacitor 플러그인

### 7.1 설정 화면 (web, 기존 설정 탭 내 서브섹션)
> **master + Capacitor 네이티브 환경에서만 노출** (`isNativePlatform() && role==='master'`). 그 외 사용자/브라우저/iOS PWA에는 미표시.

- 백업 ON/OFF 토글
- **폴더 선택** — 기기 폴더 목록에서 다중 선택(기본: 카메라), 사진만/사진+영상
- WiFi 전용 / 충전 중에만 / 배터리 부족 시 중단
- 상태: 마지막 백업 시각, 대기 N장, 진행률, 최근 오류
- "지금 백업" 버튼(수동 트리거)
- 배터리 최적화 예외 안내 진입점
- 기기 세션 목록 / 원격 로그아웃 (§5.3)

## 8. 자동 업데이트 (윈도우식)

### 8.1 서버
- `GET /api/app/version` → `{ version, minVersion, apkUrl, notes }`.
- APK 파일은 NAS에서 서빙(예: `/downloads/peanut-family-<ver>.apk`).

### 8.2 앱 동작
1. 앱 시작 시 `checkUpdate()` → 현재 versionCode와 비교.
2. 새 버전이면 **"업데이트 있음" 배너** 노출(웹 UI) + 변경점.
3. 사용자가 탭 → `downloadAndInstall(url)`:
   - APK 다운로드(진행률 알림).
   - `PackageInstaller`로 설치 세션 시작 → **OS 설치 확인 1회**(보안상 우회 불가).
4. 설치 완료 → 앱 재시작. 로그인/설정 보존(업데이트라 데이터 유지).
- `REQUEST_INSTALL_PACKAGES` 권한 최초 1회 허용 필요.

> 일상적 UI/기능 추가는 WebView가 라이브 로드라 **업데이트 불필요**. 이 장치는 네이티브 변경(백업 엔진/권한/플러그인) 시에만 사용.

## 12. 단계별 로드맵 (각 단계 = 배포 후 실기기 검증)

> CLAUDE.md "배포 후 테스트 필수" 준수. 각 단계는 프로덕션 URL/실 갤럭시 기기에서 검증 후 다음으로.

**P0. 인증 기반 (서버)**
- `device_sessions` + refresh 엔드포인트 + Bearer 지원.
- 검증: 기존 웹/PWA 로그인 회귀 없음, `/api/auth/token`으로 access 갱신 동작.

**P1. Capacitor 래핑**
- Capacitor 도입, `server.url`로 기존 앱이 **APK 안에서 그대로 구동**.
- 검증: 갤럭시 실기기에서 모든 기존 기능 동작(갤러리/육아/캘린더/노트/LLM).

> ~~P2. 개인공간 일반화~~ — **D1=A 확정으로 불필요(삭제).** 서버 가시성 변경 없음.

**P2. 백업 엔진 (네이티브, 핵심)**
- master 전용 게이트 → 권한 → MediaStore 스캔(선택 폴더) → 해시 dedup → `visibility=private` 업로드 → WorkManager + Foreground Service.
- 검증: 앱 백그라운드/종료 상태에서 새 사진 촬영 → master 개인공간에 자동 적재. 중복 미업로드. EXIF 보존. 일반 사용자 계정에선 백업 비활성.

**P3. 백업 설정 UI + 신뢰성**
- 설정 화면(master만), 폴더 선택, 조건 토글, 상태/진행률, 배터리 최적화 안내, 재부팅 재등록.
- 검증: 360/280/768/1920px 레이아웃, 토글 즉시 반영, 절전 예외 안내 동작.

**P4. 자동 업데이트**
- 버전 API + 인앱 업데이트 배너 + PackageInstaller.
- 검증: 구버전 설치 상태에서 배너 노출 → 다운로드 → 설치 → 데이터/로그인 보존.

**P5. 종합 QA & 배포**
- 폼팩터 전수(갤럭시 S/Fold 접힘·펼침/태블릿/TV), 전 CRUD/네비/애니메이션, 백업 장시간 안정성.
